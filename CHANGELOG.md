## [0.19.8] — 2026-08-07
- **The game's differentiator had no first-use guidance.** A code duel is the one thing this game does that nothing else does — serverless PVP that fits in a text message — and the Duel screen explained every *button* while never explaining the **shape** of the thing: that it is a turn-by-turn exchange, not a single sent shot. A player who fires, texts a code, and then receives one back had no way to know that is normal, or that it goes in the box further down the same screen.
- **Added a first-use card that states the loop in three steps**, then what ends it: stations take `STATION_HP` damage, first one down loses, **or it is a draw if both survive `DUEL_MAX_TURNS` turns**. Also states the two facts a newcomer would otherwise have to infer — each code carries the whole match so far (so a returned code is not a reset), and both players get every shell (D-29).
- **Shown from profile state, not a stored "seen" flag** — the same approach as the aim hint on the first campaign level, and it costs no new `Profile` field. It retires on any evidence of a code duel: a win, a loss, or a code of one's own.
- **Asserted the way the other player-facing copy is** (D-37, D-43): the numbers are interpolated from `Tuning` rather than typed, the draw is stated because a duel really can end that way, and a separate test proves the card disappears for a player who has done one.
- Caught while writing the tests: `setContent` may only be called once per test, so looping profiles over it fails with "Cannot call setContent twice per test" rather than anything about the assertion — the same Compose constraint that bit `StarBurstTest` at 0.16.2. All three profiles now compose in one pass.
- 241 tests green (167 `:core` + 74 `:app`). Lint clean.

## [0.19.7] — 2026-08-07
- **Verified what the generation fingerprint actually covers, instead of assuming it.** 0.19.5 pinned generation output across 24 specs and 0.19.6 proved it catches a real change — but "it would catch *a* generator change" is not "it would catch *the* change you are about to make". A sample size is part of a claim (0.18.2), and 24 specs is a sample.
- ✅ **Eight distinct generator paths perturbed one at a time; no blind spot found.** Caught: keeper radius, repulsor mass, pulsar radius, duel station placement, campaign station placement, Thread gate spacing, gambit proof grid. That spans layout, every non-planet body kind, both station paths, and two proof grids.
- ⚠️ **The measurement lied to me three times first, and that is the part worth keeping.**
  - **A broken harness reported every path as uncovered.** Running gradle with `-q` and `2>/dev/null` swallows the failure line, so every probe came back "NOT CAUGHT" — including paths that are certainly covered. The **uniformity** is what gave it away, and a **known-positive control** through the same harness proved it broken in one step. Reporting that result would have claimed the guard covers nothing.
  - **One probe was a compile error.** It added a duplicate constructor argument, so the module never built — and in a harness that greps for `FAILED`, a build error is indistinguishable from a passing test.
  - **Two genuine "not caught" results were no-ops, not gaps.** `OBJECTIVE_CHANCE` 0.28→0.281 and `CAPTURE_BURN_TICKS` 260→261 produce **byte-identical output across 120 specs** — five times the fingerprint's spread. No seed's draw falls in that window and no capture proof turns on that tick, so not catching them is correct behaviour.
- **The reusable rule, now an extension rule**: a negative result from a perturbation test is meaningless until you confirm the perturbation does something. Pair every probe with a known-positive control, and check the build compiled.
- 239 tests green (167 `:core` + 72 `:app`). Lint clean. **No code change**: `Generator.kt` is byte-identical, and the fingerprint proves it.

## [0.19.6] — 2026-08-07
- **Attempted the difficulty-11 generation optimisation. The one promising change is forbidden, and the guard added *one version ago* caught it on the first run.**
- **The change**: `SystemGenerator.scan` checks its early-exit bound after every *angle* (5 sample shots), so checking after every *sample* abandons a hopeless candidate up to four full flights sooner. The safety argument was careful and specific — an early-exited scan returns a *bound* not a rate; `minPossible` only rises and `maxPossible` only falls, so a tighter check fires earlier with the same verdict; and `solverHitRate` is stored only when a scan *completes* in band.
- ⚠️ **It was wrong.** `generateLayout` keeps a nearest-miss fallback — `if (rate > 0) { … best = candidate.copy(solverHitRate = rate) }` — which consumes the early-exit bound **directly and stores it**. A tighter bound changes which candidate is "best" and therefore changes the generated level. Worse, the fallback is the path *hard difficulties take most often*, so the damage would have been largest exactly where the optimisation was aimed.
- **`GenerationFingerprintTest` failed immediately** — added in 0.19.5, paid for itself on the very next change anyone attempted. Without it this ships as "a safe optimisation" and silently invalidates every share code in existence. **A careful argument for output-preservation is not a substitute for the guard: this argument was careful, specific, and false.**
- ⚠️ **Second finding, against my own measurement.** I recorded the change as a real speedup — d11 worst case 216ms → 102ms. It was not. The reverted, unmodified code measures **100ms** under the same warm conditions: the 216ms baseline was a *cold-JIT* first measurement, so the comparison was cold-versus-warm. That is the exact error PERFORMANCE.md exists to forbid, quoted in this repo's own extension rules, and I made it anyway. The speed benefit was never established — and the change is forbidden regardless of speed.
- **Profiled breakdown for d11**, which refines what TODO recorded: `scan` **63%** of time across only ~10 calls per 4 generations; `fallsToNaiveShot` **20%** across ~121 calls (it rejects ~92% of candidates before they reach a scan); `anchorLeverage` **1%**; objective proofs and overhead ~15%.
- **TODO's "~684ms worst case" is stale and machine-relative** — on this machine it is ~100ms warm / ~216ms cold. Corrected in place with the caveat.
- Remaining safe avenues are genuinely narrow: **no floating-point rearrangement is permissible**, because non-associativity changes results and therefore the protocol. Only exact-value caching and allocation reduction remain, and neither was shown to help.
- 239 tests green (167 `:core` + 72 `:app`). Lint clean. **No code change**: `Generator.kt` is byte-identical to 0.19.5, and the fingerprint proves it.

## [0.19.5] — 2026-08-07
- ⚠️ **Nothing in the repository could detect generation output changing — the one change that breaks every share code in existence.** Found while preparing to optimise difficulty-11 generation, where TODO's own constraint is that "only optimisations that provably preserve output are allowed". There was no way to prove it.
- **Why it matters more than it sounds.** A replay code carries `(mode, difficulty, seed, turns, hash)` and `decodeAndVerify` **regenerates the board from the seed**. A generator that drifts by any amount silently invalidates every code ever shared — and the failure surfaces on a stranger's phone, not in CI.
- **What was guarding it**: `generationIsDeterministic`, which asserts `generate(12345L, 3) == generate(12345L, 3)`. That is determinism *within one run, on one seed, at one difficulty*. It would pass unchanged if the generator were rewritten to produce entirely different levels. Same defect class as 0.19.0's Help gap — a guard only checks what is enumerated in it — but applied to the most protocol-sensitive code in the project.
- ✅ **`GenerationFingerprintTest` pins the whole thing**: body geometry, masses, kinds, palettes, velocities, stations, gates, objective, marked body, and the measured `solverHitRate` / `anchorLeverage` / `gambitMasks`, across 24 specs spanning six difficulties plus the daily and duel generators, folded to one constant. Doubles go in by raw bits, because D-4 already guarantees they are bit-stable and anything looser would hide exactly the drift worth catching.
- **Verified in both directions rather than assumed — a guard nobody has seen reject something is a guard being taken on trust.** Perturbing one layout constant by **0.001** (`keeperR` upper bound 86.0 → 86.001) makes it fail. Running the **entire core suite** against that same perturbation, **it is the only test that fails**: `ShareCodecTest`, `EndToEndPvpTest`, `GeneratorTest` and `generationIsDeterministic` all pass against a changed generator.
- The failure message says what to do, because the tempting fix is the wrong one: a changed fingerprint means **either revert, or bump `ShareCodec.VERSION` deliberately** and update the constant in the same commit with a decision entry. Pasting the new number in turns a protocol break into a rounding error.
- This unblocks the difficulty-11 generation work, which could not honestly have been attempted without it.
- 239 tests green (167 `:core` + 72 `:app`). Lint clean. **No engine change**: the generator is untouched, and the fingerprint proves it.

## [0.19.3] — 2026-08-07
- **Stage E's resonance mechanic has no subject: a player cannot fire "in phase", because every shot resets the pulsar.** VISION §3.4 says *"fire in phase and the assist amplifies; fire out of phase and it fights you"* — a choice that does not exist in this game. `massAt(tick)` reads `LiveShot`'s own counter, which starts at **0 for every shot**, so every shot ever fired meets a pulsar at `cos(0)`, its heaviest.
- **Demonstrated at match level rather than argued from the constant**: an identical aim fired as turn one and as turn two is **bit-identical** — same hash, same tick count (`ResonanceReachTest`). Phase varies *within* a flight, which is what makes a pulsar worth flying past, but never *between* shots. There is no timing to get right, so there is nothing to reward.
- The ambience is **consistent with this and not implicated**. D-33 says playback seeks to sample zero on fire precisely because the pull does too, so "the swell you hear is the pull the shot is flying through" remains true.
- 💰 **Costed, so the decision is real**: making it work means pulsar phase becomes a function of match time rather than shot time, which changes what every existing pulsar level does — a **protocol break**, not a tuning change — and touches **27% of systems** (98/360 measured, none below difficulty 4). Making it a *choice* rather than an artefact of turn order additionally needs a timing input recorded in `TurnInput` and folded into the hash, since a phase the sender picks but never transmits is unverifiable in exactly the way D-23 cut Blind for.
- ⚠️ **Second finding: the polyrhythm half has no subject at all.** TODO said "the generator never makes two [pulsars] with different periods", which reads as *two exist and share a period*. They never co-exist — **0 of 360 systems have two pulsars**. The item is blocked on something more basic than a per-body period: there is only ever one pulsar to give a period to.
- **That is the third documented feature this session whose premise the generator does not produce** — the binary star that does not exist (D-41), the Dark run that never blinded anyone (D-43), and now this. The pattern is worth naming: a design document describes what the game *should* be, and nothing fails when the generator quietly never gets there.
- 238 tests green (166 `:core` + 72 `:app`). Lint clean. **No engine change**: this release is a measurement and two corrections.

## [0.19.2] — 2026-08-07
- **Field-shaping mutators: decided against, and the arithmetic says why.** 0.19.1 proved the obvious implementation impossible and identified a sound one (seed selection). This closes the question rather than leaving it open forever, because a viable route whose price never closes is a decision, not a backlog item.
- **Availability was never the problem** — I had framed it as one, and the framing was wrong. An Uncharted leg's difficulty is `min(11, 2 + depth/2)`, so it reaches 6 at **depth 8** and 8 at **depth 12**: 3 of 15 junctions eligible in a rough run, 10 of 22 steady, 15 of 27 expert. Roughly half of every run archetype qualifies.
- **The price is the problem, and the two honest implementations land on opposite sides of usable:**
  - **Generate once, label only if the system genuinely is dense.** Costs one generation (~110ms) and can never lie. But the measured hit rate at difficulty ≥8 is 13/60, and Uncharted carries one of four conditions, so it would appear **0.16–0.81 times per run** — once every two to six runs. That is an easter egg, not a mechanic.
  - **Search seeds until one is dense.** Real availability at **0.75–3.75 offers per run**, but ~390ms desktop (1–2s on a phone) at a junction — and `Expedition.routesFor` is called *directly in composition*, twice per junction, so it would need memoising just to avoid repeating per frame.
- **The structural reason is worth keeping: knowing what a field looks like requires building it.** That is exactly why the shipped conditions are cheap — *Thin reserves* is fuel arithmetic and *Dark run* is a UI flag, both free to evaluate — and why a field condition is not. A condition a player meets twice a year does not justify a second of stall at every junction.
- Reopen only if generation gets substantially faster; the route is proved sound, only its price fails.
- 235 tests green (163 `:core` + 72 `:app`). Lint clean. **No code change**: this release is a decision.

## [0.19.1] — 2026-08-07
- **Field-shaping mutators: the obvious implementation is impossible, and a viable one exists.** D-34 deferred *binary star ahead*, *anchors doubled* and *dense field* on honesty grounds — each asks the generator for a layout it may not produce, so each needs a proof the mutator took. That reason was real but it was the weaker one.
- ⚠️ **The binding constraint is architectural, and it is now proved rather than argued** (`MutatorReachTest`, four cases). A share code carries `(mode, difficulty, seed, turns, hash)` and nothing else; `decodeAndVerify` regenerates the board from the seed; and **every match can emit a code** — an Expedition leg included, via the feedback report, which is how agents triage bug reports. So a mutator that changes *what the board is* produces a leg whose own replay code **cannot verify**: the receiver rebuilds the unmutated board and rejects it as forged. Measured directly — a leg played with one extra body fails `decodeAndVerify` while an unmutated control passes.
- ***anchors doubled* is dead outright, and for a sharper reason.** `ShareCodec.decode` enforces `MAX_ANCHORS` as a **rule check**, which is what stops a forged code claiming a match played with more anchors than the game allows. Raising that cap to suit one Expedition mutator would weaken verification in **duels**, where verification is what decides who won (D-29). A solo mode's convenience is not worth a hole in the PVP guarantee.
- **This also explains why the two shipped mutators are safe** — *Thin reserves* acts on fuel economy and *Dark run* on the aim trace, neither of which a code depends on. Now asserted structurally instead of being true by luck.
- ✅ **Seed selection is the open route.** Do not ask the generator for a favour: search its *natural* output for a seed that already satisfies the condition and offer that one. The code then carries an ordinary seed whose plain regeneration reproduces exactly the board played, so verification is untouched — demonstrated by a seed-selected dense leg verifying normally. It also answers D-24 for free: **the search predicate is the proof**, and a search that finds nothing offers no mutator, which is the honest failure rather than a false claim.
- 📏 **Costed, so the decision is real rather than speculative.** Natural body counts run 2–4 at difficulty 2 and 3–8 at difficulty 8+, so *dense field* (≥7 bodies) is **unreachable below about difficulty 6**: 0/60 at d2 and d4, 1/60 at d6, 13/60 at d8, 14/60 at d11. A 24-seed search at d4 burns **2061ms to find nothing**. Where it does exist it takes ~5 tries and **~390ms desktop** — 1–2s on a phone, on top of the leg's own generation. Buildable, but only deep in a run, and only if the search is paid at junction-offer time rather than at level start.
- The PR body was refreshed for the first time since 0.18.0, because 0.19.0 changed player-facing behaviour (Dark run actually blinds now) and a stale body understates a behaviour change rather than merely a version number.
- 235 tests green (163 `:core` + 72 `:app`). Lint clean. **No engine change**: this release is a proof, a measurement and a decision.

## [0.19.0] — 2026-08-07
- **Blind finally ships, in the one form that survives the objection that cut it.** D-23 removed *Blind* from the scored declarations because nothing in a `TurnInput` records whether the sender looked at their preview — a peer verifying a share code would have to take it on trust, which is a hole in a game whose premise is that nothing is. It shipped here as a **Settings toggle** that removes the aim trace everywhere, including duels, and **pays nothing**: no bonus, no multiplier, no star, nothing recorded, nothing transmitted. The objection was always about verification *by a stranger*, and a handicap that grants no reward gives a stranger nothing to verify.
- Blind practice is checked **before** the duel branch, deliberately. A duel guarantees both players the top preview (D-29), but that rule exists to stop anyone being *disadvantaged* — it must not override a disadvantage the player chose for themselves.
- ⚠️ **Building it found that Expedition's *Dark run* had been lying since 0.15.0.** The mutator's own description reads "No aim trace on this system", and D-34 recorded it as "Blind ships at last" — but `previewLevelFor` returned tier **0**, which is not blindness. Tier 0 is the base 90-tick trace every player already owns. The mutator was removing a *purchase* while the copy promised the trace, so a player who had never bought a preview upgrade experienced a Dark run as **no change whatsoever**.
- **Fixed with a tier that actually means none** (`Economy.PREVIEW_NONE`), handled in an explicit branch rather than by falling through — a negative tier hitting the old `else` would have returned the *best* preview, the exact inverse of the intended rule.
- **Why the test did not catch it**: `ExpeditionTest` asserted `previewLevelFor(blind) == 0` — pinning the implementation rather than the claim, so it guarded the bug instead of finding it. It now asserts the result in **ticks**, which is what the description actually promises.
- ⚠️ **Second omission, found the same way: debris shipped in 0.18.0 with no Help entry at all.** A permanent obstacle appears on the player's own board when they miss, and for a whole version nothing in the app explained it. `HelpAccuracyTest` exists precisely to prevent that and could not fail, because its topic list is hand-maintained and nobody had added a line. Help now carries a wreckage card, and the list carries the entry.
- **Both failures share one shape, recorded because it will recur: a guard only checks what is enumerated in it.** Adding a mechanic without extending the list makes the guard silently incomplete rather than loudly wrong — the same defect class as 0.18.2's sample-size problem, one level up.
- 229 tests green (157 `:core` + 72 `:app`). Lint clean. Release APK 1.73 MB.

## [0.18.2] — 2026-08-07
- **Answered the open question from 0.18.0 — should a wreck pull? No, and the reason is that its safety cannot be tuned.** Mass was deliberately held at 0 so that "obstacle" and "gravity" were not conflated inside one measurement. Measured now across 30 levels at five masses, massive debris drives levels to a *zero* solve rate **non-monotonically**: 1e4 → 3/30, 2.5e4 → 2/30, 5e4 → 0/30, 1e5 → 1/30, 2e5 → 2/30. There is no "safe if small" threshold to aim at, because small is not safer. That is the signature of a compounding mechanic — a massive wreck bends later shots, which changes where they die, which puts the next wreck somewhere the clean board never would have — and it is exactly why D-40 refused to inherit the massless safety argument instead of assuming it carried over.
- **The measurement caught itself lying before it produced that answer.** The first run reported byte-identical numbers for every mass including 2e5, which reads as a clean "mass is irrelevant, ship either way". The cause was my own 0.18.0 optimisation: the integrator skips `BodyKind.DEBRIS` whole, *before* the arithmetic, precisely because a shipped wreck is massless — so a probe built out of `DEBRIS` was measuring nothing at all. Rows that agree **too** exactly are evidence of a disconnected instrument, not of a robust result.
- ⚠️ **Correction to 0.18.0: the "nothing strands the player" claim was true of nine levels, not in general.** D-39 asserted it across 27 configurations and D-40 inherited it; `measureStrandingAtFullMatchLength` asserted it and passed. Widening the sample from 9 levels to 30 found the **shipped, massless** configuration stranding 2 of them. The assertion had quietly dropped the sample size from the claim — "no level in my sample stranded" is not "no level strands".
- **The severity, stated precisely rather than softened.** Earliest stranding is **13 wrecks**. Campaign caps at 4 shots (≤3 wrecks) and daily at 5 (≤4), so **neither can reach it**, and because objectives are campaign-only (D-27) **no objective can be stranded** — the 29-system objective re-proof from 0.18.0 stands. Only a duel reaches 13+, at up to 30 turns, and there an unwinnable board is a **draw at the turn cap** — an outcome D-37 already documented — not a dead end a player cannot leave. So the shipped behaviour is fine; the claim about it was not.
- **The guard moved to the bar that carries consequences.** `measureStrandingAtFullMatchLength` no longer asserts a general no-stranding property it cannot support; it keeps reporting retention, which is still the useful number. The new assertion lives in `measureHowMuchLitterItTakesToStrand` and says stranding must stay *out of campaign reach*, which is where objectives live and where a dead end would actually be a dead end.
- 226 tests green (155 `:core` + 71 `:app`). **No engine change**: this release corrects claims and guards, not behaviour.

## [0.18.0] — 2026-08-07
- **Stage F ships: a shot that dies on a world leaves a wreck, and every later shot this match has to fly around it.** VISION's last unbuilt stage, and the final one on the roadmap. Built directly from 0.17.2's measurements rather than from the original sentence, which the numbers had already contradicted (D-39).
- ⚠️ **Protocol v9 — but the first bump that spends no bytes.** Every earlier version changed what a code carries or what a seed generates. Debris changes neither: a wreck is a pure function of turns the code already holds, so a verifier re-derives it without being told any of it. What changed is the **meaning** of a code, not its shape — the same (seed, turns) now produces a different match, so pre-v9 codes are refused. `DebrisTest.aReplayDerivesTheSameDebrisWithoutBeingToldAnyOfIt` is the load-bearing proof.
- **Four rules the measurement could not settle, decided and tested:**
  - **A station kill leaves nothing.** That is an outcome, not a crash — and it keeps out the one pathological case, since a lump welded to a launch point would be a self-inflicted dead end. Measured at 1 own-station death in 18,000 samples: real, rare, and worth excluding by rule rather than by luck.
  - **One wreck per turn, even from a Triad's three shards.** Per-shard litter would triple a duel's accumulation and carry it past the 30 lumps actually measured. A turn leaves a wreck, not a shard count.
  - **Litter cannot breed litter.** A wreck settles against a world, never against another wreck, so accumulation stays linear in turns instead of compounding.
  - **Debris is inert for scoring.** It is skipped in the deflector count and the graze bonus. This one is not cosmetic: `deflectorCount` decides the "two-body" gambit, so without it a declaration could have been honoured by skimming a massless lump — a deflection that never physically happened.
- **Objectives were re-proved under litter before this shipped.** 0.17.2 measured whether a littered board still has a shot that *hits the enemy station*, but three of the four objectives are not won that way, and they are the fragile ones — a wreck can fence a capture ring or sit across a thread gate. 29 objective systems (13 Capture, 12 Thread, 4 Courier) were littered at the reachable campaign envelope and re-proved: **none became unwinnable.** D-27 forbids setting a task the arena cannot pay, and that bar now applies to boards the player littered themselves.
- **The aim preview flies the littered board too.** It was reading `spec.bodies`, which stopped describing the field the moment a wreck existed — so the line on screen would have been a trajectory through a board the shot was never going to meet. The preview is the instrument the player judges the shot with; it does not get to be out of date.
- **A hole that turned out to be closed by arithmetic already in the code.** The daily relocates its target after each hit, and its clearance test reads `spec.bodies`, so it cannot see wrecks. It does not need to: a relocated target sits at least `bodyRadius + 76` from a body's centre while a wreck sits at most `bodyRadius + 9` from it, leaving a gap of ≥67 against the 38 needed to overlap. Pinned in a test rather than left as a lucky margin, because it is only true while those constants hold.
- **Performance**: debris is skipped at the top of the integrator's body loop rather than filtered afterwards. It is massless and contributes nothing to acceleration, so a duel carrying 30 wrecks would otherwise pay 30 needless square roots per projectile per tick — in the single hottest loop in the game — to add exactly zero.
- **Rendering**: wrecks draw as cold grey silhouettes with a broken outline, deliberately the only thing on the board that emits no light. Every other body glows, pulses or catches a rim light; a wreck must read at a glance as spent matter that blocks but does not pull, because that is precisely what it is.
- Also fixed while here: TUNING.md's protocol history stopped at **v5** and was four versions stale.
- 151 `:core` tests (11 new in `DebrisTest`, 1 new measurement in `DebrisMeasurementTest`) + 71 `:app`, all green. Release APK unchanged at 1.73 MB.

## [0.17.2] — 2026-08-07
- **Stage F debris was measured before it was written, and the measurement rewrote the rule** (D-39, `DebrisMeasurementTest`). VISION §3.3 has promised since the start that "a shot that dies leaves debris at its death point — miss twice and you have complicated your own board". Three of that sentence's assumptions did not survive contact with the simulator.
- **The obvious sample was the wrong sample, and it pointed the wrong way.** Swept over the solver's uniform 360° grid, 86% of shots leave the field and only 12–19% die on the board — which reads as "debris is inert, the mechanic is dead". But that grid includes firing directly away from the target into empty space, which no player does. Re-sampled inside a realistic aim cone the number **inverts: 57–80% of misses die on a body.** Same simulator, opposite conclusion, decided entirely by which shots you ask about. Taking the first number at face value would have cancelled the feature on a false negative.
- **Debris can never appear in open space.** A shot has essentially one way to die on the board, and that is hitting a body: 18,000 samples gave 2,625 body deaths, **1** own-station death and **0** timeouts. So debris always lands against something already solid — it cannot block an empty lane, and no rewording of "at its death point" changes that. The own-station case is real but pathological (a lump welded to your own launch point) and is excluded by spawning on body impact only.
- **The physically honest version is invisible.** Area-conserving accretion — add the shell's cross-section to the body it struck — takes a radius-100 planet to 100.12, and across 16 hits at every difficulty the solve rate did not move by a single sample. Bodies are radius 58–101 against a radius-5 Bolt. Conserved matter cannot register, so debris has to be sized for legibility rather than for physics.
- **What works is that a lump is directional.** It sits on the side the shot came from, so it obstructs *the approach you keep taking* — which is the actual content of "the arena degrades into something neither player designed". Growing the struck body's radius instead would be isotropic and say nothing. Measured against solvability, erosion is gradual and scales with size: at radius 12 a level keeps 50–100% of its winning shots after 30 lumps; at radius 20, only 33–67%.
- ~~**Nothing stranded the player** across 27 configurations, including 30 lumps — worse than the 30-turn cap can produce — at radius 20 on difficulty 11.~~ **⚠️ Superseded by 0.18.2 (D-42): this was true of the nine levels sampled, not in general.** Widening to 30 levels found two that a littered board makes unwinnable, the earliest at 13 wrecks — out of reach of campaign (≤3) and daily (≤4), reachable only in a duel where it is a draw at the turn cap. The measure was otherwise conservative as described (STANDARD shells, one station, no anchors), and `measureStrandingAtFullMatchLength` did assert the property — which is precisely how a sample-sized claim shipped as a general one.
- Recommended rule, recorded for the implementation unit: **radius ~12, mass 0, on body impact only**. Whether debris should also *pull* is left open on purpose — mass was held at 0 so that "obstacle" and "gravity" were not conflated inside one measurement.
- **Corrected a piece of my own reasoning that was blocking three items.** TODO recorded "do these protocol bumps in one bump or not at all", justified by "two separate bumps invalidate every code in the wild twice". There are **zero codes in the wild** — no Play release, no GitHub release, no git tag, and the Console account is not yet created. A bump today invalidates nothing. Batching is a real economy after launch and an imaginary one before it, and treating an imaginary cost as a blocker had stalled multi-pulsar polyrhythm, travelling trails and Stage F debris alike. Noted with the date it stops being true: the first tester install.
- Method note kept in D-39 because it nearly produced a false structural claim: the first version of the assertion read `0.0%` off a formatted column and asserted zero. The raw count was 1. A rounded display is not data.
- `:core` test output now streams by default (`showStandardStreams`), because several tests in that module are measurements whose *numbers* are the deliverable and they should not need `--info` and a grep to read.

A doc that contradicts itself is worse than one that is merely out of date, because both halves look authoritative. Corrected, with the original complaint kept and answered rather than deleted.

## [0.14.0] — 2026-08-06
- **The game has music.** It had none at all — the single largest presentation hole, and the one that could not be filled by writing some, because every level here comes from a seed and there is no finite set of places to score. One shared background loop would have said nothing about where you are.
- **So the pad is generated from the board.** Each body that matters gets a voice: pitch from its mass (heavier sits lower), phase from its position, tremolo from its kind, and the whole chord drawn from an interval set chosen by the **objective** — Breach is bare fifths, Capture is minor and unresolved, Courier refuses to settle, Thread is the only one that sounds resolved. A system with one huge star and two pebbles does not sound like three even worlds, because it is not.
- **A pulsar's voice swells at the pulsar's real gravity period**, and that is the point of the whole feature: the field can now be learned **by ear** before it is a rule. `PULSAR_PERIOD × DT` is exactly 3.5 seconds, so the loop is **7 seconds** — the smallest whole number of seconds holding a whole number of pulsar cycles. Because the loop is an integer multiple of the period, looping forever never drifts out of lock, and the app seeks to sample zero when you fire so the swell you hear is the pull the shot is flying through. This is VISION Stage E's sonification half, taken early (D-33).
  - The claim is scoped honestly in code and docs: the tremolo runs at the pulsar's rate always, but it only reports *phase* because playback restarts on fire. Systems with no pulsar skip the seek entirely — there is nothing to learn from locking a system with no pulse.
  - A test fails loudly if a future retune of `PULSAR_PERIOD` breaks the divisibility, because the game would otherwise go on claiming the pad tracks the pull.
- **The loop is seamless by construction, not by tuning.** Periodicity is stored as *integer cycles per loop* rather than hertz — frequency is the derived quantity — so a clicking seam is not a bug that can be introduced, and the same holds for every tremolo. Verified the way an ear would check it: the step from the last sample to the first must be no larger than the largest step anywhere inside the loop.
- **And it is exactly in tune at the same time**, which normally fights seamlessness — snapping frequencies to a loop grid detunes the intervals, and pure intervals put the seam back. They stop fighting if the root comes from a divisible grid: every root is a multiple of 80 cycles and every ratio denominator divides 80, so exact just intonation and an exact seam hold together with **no rounding anywhere**. Detuning is then deliberate — one cycle per loop is 1/7 Hz, so two voices beat once per loop and the beat loops seamlessly too. Without it, a sum of pure tones is dead air.
- **Zero APK bytes and zero CPU while playing.** Nothing is shipped; the loop is computed on a background thread in ~40ms (desktop) once per system, then handed to the audio HAL with `MODE_STATIC` hardware loop points, so an hour of drone costs no application CPU. That option only exists *because* the seam is exact — a seam would have forced a crossfading streamer and a thread to run it for the whole match. The mathematics pays for itself in battery.
- **`./gradlew :core:ambienceWav` writes sample pads to .wav.** Sound is the one generated thing here that measurement cannot sign off: a loop can pass every assertion and still be unpleasant to sit inside for ten minutes. The seven SFX have been un-auditioned since 0.2.0 purely because listening seemed to need a device. It does not need a device — it needs a file.
- **Ambience is its own setting**, separate from sound effects, because wanting a hit to land audibly and wanting a drone underneath it are different wants; collapsing them forces anyone who objects only to the second into silence.
- Deliberately **outside the determinism contract**: never hashed, never simulated against, never on the wire. Two devices replaying a duel hear the same pad because they generate the same system, but nothing checks that and nothing should — the day verification depends on an audio buffer is the day audio tuning becomes a protocol break. No protocol bump; every existing challenge code still verifies.
- Docs: new **docs/AUDIO.md** (both sound systems, the tuning mathematics, the honest scope of the pulsar claim, and the open questions for the first playtest); D-33; ARCHITECTURE, PERFORMANCE, VISION §3.4/Stage E and the release QA checklist updated.
- Two stale entries found in the ARCHITECTURE file map while adding the new ones and fixed: `BodyKind` was still listed as STAR/PLANET/REPULSOR (comets and pulsars have existed since 0.4.0) and the IAP count still read "3 INAPP" after `season_pass` made it four.
- Tests: 162 (104 `:core` + 58 `:app`), 10 new.

## [0.13.0] — 2026-08-06
- ⚠️ **Protocol v8.** A third objective adds gates to the spec, changing what a seed generates again, so v7 codes are refused.
- **Thread: fly through the gates in order** — VISION Stage C is now complete (Capture, Courier, Thread).
- **The order is the objective**, and it is enforced rather than implied: a flight that physically passes through all three gates in the wrong sequence has threaded nothing. A test drives exactly that case — same shot, same gates, listed in the order it cannot meet them — and requires it to lose.

Before firing you may declare a constraint — *Featherweight* (under 40% power, ×1.5), *Two-body* (pass through the pull of two different worlds, ×1.8), *Stolen speed* (end faster than you launched, ×1.6), *The long way* (never cross the line to the target, ×2.2). Keep the promise and the shot pays the multiple. Break it and the shot is wasted: the hit does not land. That stake is the point — it turns mastery into something risked rather than something displayed, which is what the word has meant all along.
- **VISION's "Blind" gambit was cut, not implemented.** It was the one proposal the physics cannot see: a peer verifying a share code re-runs the simulation and derives everything else from the flight, but nothing in the inputs records whether the sender looked at their aim preview. A scoring rule that has to be believed, in a game whose whole premise is that nothing is believed — and one paying a multiplier, which is exactly where cheating pays — is a hole. The four that shipped are each decided by the simulation. (D-23)
- **The menu is proved per level and per seat.** The first pass offered all four everywhere; measuring twelve curated levels found *Two-body* had **zero** winning shots on three of them. The game would have been inviting a bet it could not pay. The generator now proves feasibility and offers only what it found — and per seat, because intersecting both seats left half of sampled duels with nothing to declare at all, and the two stations genuinely face different fields. The proof is conservative by construction: every option offered was set by a real simulated hit, so the sweep can under-report but never invent. (D-24)
- **Fixed a design bug found while building it**: a kept declaration multiplied *style points*, which duels never read — duel outcome is HP and nothing else. Declaring in PVP was therefore all risk and no reward. A kept declaration now multiplies **damage**, the currency the mode actually settles in. (D-25)
- **"Stolen speed" was recalibrated from measurement, not feel.** At the first threshold it was satisfied by roughly nine winning shots in ten — a declaration nearly every hit honours is not a stake. Across 201 winning shots on twelve levels the median gain was 101; the threshold moved to 120, near the 80th percentile.
- Three stars now also recognise a kept declaration as having worked the field, and a hit inside a broken declaration can no longer be the winning shot — because it did not land.
- **Proving all this costs nothing.** A dedicated feasibility sweep measured 300–500ms on hard levels. The solver sweep the generator already runs simulates every sample shot to completion and `ShotResult` already carries the measurements, so feasibility now rides along on it for four comparisons per winning sample. The dedicated sweep survives only as a second opinion for seats that came back empty.
- Tests: 116 (66 `:core` + 50 `:app`), 20 new.

## [0.8.0] — 2026-08-06
- **Aiming is a floating joystick.** The stick now appears wherever the finger lands and reads the pull *relative to that point*, instead of being anchored to the station. Anchoring it there meant the gesture lived permanently in one screen corner: the thumb covered the play area it was aiming into, and the reachable arc was clipped by the screen edge — you could not pull "past" the corner, so half the aim space was hard to reach and the other half was hidden under your own hand. Pull back to aim the opposite way; the arrow reads as a slingshot rather than a steering wheel.
  - Built on a hand-rolled `awaitEachGesture` rather than `detectDragGestures`, because the latter only reports its origin *after* touch slop is exceeded — the ring would have appeared a few pixels off the finger and one gesture-slop late. It now centres on the true touch-down and is visible from the first frame.
  - Drawn as a dead-zone ring (so "inside here does nothing" is visible, not folklore), a power arc, the pull line, and a heading spike tinted cyan→yellow with power.
- **Fine-tune buttons repeat on hold.** They were single-tap only, which meant ~450 taps to swing the aim 45°. Press and hold now auto-repeats after 320ms, and the *step itself* grows the longer it is held (×1 → ×3 → ×8, with a haptic tick at each change), so one control covers "a hair to the left" and "swing it right round". A tap is still exactly one step — the immediate step fires on press, not on release, so a tap shorter than a frame still counts.
  - The rewritten control is a raw pointer target, which carries no semantics of its own, so its TalkBack role and single-step activation are now declared explicitly rather than inherited from `TextButton`.
- Portrait control reserve 188dp → 196dp: the fine-tune targets grew to a 48dp minimum (accessibility touch target), and reserved rows are how this layout avoids covering the board.
- Tests: 103 (55 `:core` + 48 `:app`; two new: aim is origin-relative across distant touch points, and the dead zone does not steer while the stick clears on release).

## [0.7.0] — 2026-08-06
- ⚠️ **Protocol v4.** Curated generation and the longer solver horizon change what a seed produces, so older codes are refused rather than replayed into a different universe.
- **Levels now have a purpose.** A player cleared a level with a straight shot, used no gravity, and took three stars — and they were right that the level had none. Measurement confirmed it was systemic: **5 of 36 campaign levels fell to a near-straight shot.** Two root causes, both fixed:
  - The generator scattered bodies with only *separation* rules and never asked whether the direct station-to-station corridor was blocked. Layouts are now built **around the shot they want to force**: stations first, then a **keeper** placed on the direct line and sized to eclipse it, then **shepherds** alternating either side at offsets that make a curved route plausible. Placement with intent, not rejection-sampled randomness.
  - The solver measured *what fraction of the whole aim space connects*, which says nothing about *whether the first thing anyone tries works*. `fallsToNaiveShot` now rejects any level beatable by pointing within 22° of the target at any power — including every fallback path, which was quietly reintroducing the exact bug it was meant to guard against.
  - Result: **0 of 72 levels across six sectors fall to a straight shot**, average 4.7 bodies per level.
- **Three stars now mean "you played the game".** Shot count alone gave full marks for a lucky lob; the third star additionally requires the winning shot to have worked the field — stolen speed from it, curved, or struck a comet.
- Difficulty bands recalibrated: they were tuned for open corridors that no longer exist, and difficulty 0 was landing *below* its own floor, silently pushing early levels onto the fallback path. The solver horizon also rose 600→950 ticks, because curved routes take longer than lobs and genuine solutions were being scored as misses.
- Generation got **~20× faster** (17–40ms, from 300–630ms) as a side effect: curated layouts are accepted on the first attempt instead of burning 24 random ones.

## [0.6.0] — 2026-08-05
- **The difficulty solver stopped lying.** Anchors let players bend the field, so a hit-rate measured on a *fixed* field no longer describes how hard a level is — the game's "measured difficulty" guarantee had quietly become false the moment anchors shipped. `anchorLeverage` now measures the thing that actually matters: **of the shots that currently miss, what fraction can a single anchor rescue?** Systems where anchors trivialize aiming are rejected.
- Corrected a design error of my own along the way: the first version also demanded a *minimum* leverage ("anchors must matter here"), which rejected perfectly good pure-aim layouts — variety in how much anchors help is a feature — and each rejection costs another full solve sweep, tripling generation time. Measure always, reject only trivialization.
- Recorded an honest open question: duel generation measures ~330ms. Stashing the probe showed ~324ms without it, so this is not the probe — duels solve the aim space from both stations and 0.4.0's comets/pulsars added bodies to every sim. Logged as an optimisation target rather than left as folklore.
