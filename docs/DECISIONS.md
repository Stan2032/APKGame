# DECISIONS.md — architecture decision records (dense)

Format: D-n · decision · why · revisit-when. Statuses implicit: all ACTIVE unless marked.

- **D-1 · Game = deterministic N-body artillery duel ("Gravity Gambit")** · physics generates infinite depth from zero content; artillery = proven genre with no honest-physics mobile entry; determinism unlocks D-2 · revisit: never (identity).
- **D-2 · Serverless multiplayer via verified replay codes; no accounts, no backend** · $0 infra (user constraint), works day-one with zero install base, physics-as-anti-cheat · revisit: when DAU justifies realtime (v2 WebRTC lockstep — additive, not replacing).
- **D-3 · ~~v1 ships with NO INTERNET permission~~ CORRECTED 2026-08-04** · We declare none, but the MERGED manifest carries INTERNET + ACCESS_NETWORK_STATE from `com.google.android.datatransport` (transitive via Play Billing). Discovered by auditing the built APK with aapt2 — the claim had been asserted from our source manifest, never verified against the artifact. **What remains true**: our code has zero networking, the game is airplane-mode-complete, and we collect/transmit nothing. **What changed**: all "no internet permission" wording (privacy policy, Settings, store copy, README, checklist) corrected to describe *behavior* rather than the permission list. **Not stripped** via tools:node="remove": Play Billing may rely on it at runtime and breaking purchases to win a marketing line is a bad trade — revisit only with a device to test billing against. Guarded going forward by tools/verify_release_apk.py, which fails on any permission outside an explicit allowlist. Lesson recorded: verify claims against artifacts, not sources.

Purchases may now grant real progression (shells, aim traces, the season pass); the invariant is specifically that **none of it reaches PVP** · revisit: pricing after real eCPM data; never the fairness principle.

- **D-17 · Portrait-first fixed world 1000×1600; on wide screens the HUD moves into the letterbox bars** · one-hand casual aiming keeps the portrait board, but measurement showed ~65% of a landscape phone screen was empty bars with the HUD floating over play. - **D-20 · ~~Session branch is repo default; no PR flow~~ SUPERSEDED 2026-08-06 · `main` is now default** · The repo was born empty, so its first push made `claude/google-play-apk-game-139njt` both the default *and* the only branch — a branch cannot open a PR into itself, which is why no PR ever existed and every change landed straight on the repo head. On the owner's offer, `main` was created at that branch's tip (full history, not an empty root) and the owner switched the default over. **Flow from here**: development continues on `claude/google-play-apk-game-139njt`; `main` moves only through draft PRs that CI has passed; release tags come off `main` · revisit: if the branch naming ever outlives this session.
- **D-22 · Orbital motion (v2) needs NO engine restructuring — assessed 2026-08-04, not built** · Question: does `MatchEngine`/`LiveShot` need reworking before bodies can move? Assessment: **no**. Body positions are read in exactly two places in the hot loop (`integrate` gravity accumulation, `collide` overlap test) and nowhere else in the rules; `Body` is already an immutable value type, so motion is a pure function `pos(tick)` rather than mutable state — determinism is preserved for free provided the position function uses only the sanctioned operations (StrictMath, doubles; see DETERMINISM.md) and takes the *integer tick* as its input, never wall-clock. Required changes are additive: (a) `Body` gains orbit params (centre, radius, angular velocity, phase) with static bodies as ω=0; (b) the two hot-loop reads call `bodyX(b, tick)`/`bodyY(b, tick)`; (c) `RenderCache` must stop precomputing body centres and instead cache only orbit *geometry* (per-frame positions become cheap trig — measure before shipping); (d) the solver already re-simulates per candidate so it keeps working unchanged, though generation cost rises since layouts can no longer be pre-culled by static geometry. **Blocking consequence**: every existing share code breaks, so this is a `ShareCodec` VERSION bump (TUNING.md §Versioning) and — post-1.0 — a SemVer MAJOR. Verdict: build it when the gameplay is worth the protocol break, not before; no preparatory refactor is justified now, and doing one speculatively would add indirection for a feature that may never ship.
- **D-23 · Gambits are scored ONLY if the simulation can verify them; "Blind" is cut** · VISION.md §3.2 proposed four declarations including *Blind* (fire with no aim preview). Three of the four are properties of the flight — power used, bodies passed, path relative to the launch→target line — and a peer re-running the physics from a share code derives them itself. *Blind* is not: nothing in a `TurnInput` records whether the sender looked at their preview, so a receiving device would have to take the claim on trust. In a game whose entire premise is that nothing is taken on trust (D-2, D-4), a scoring rule that only works if everyone is honest is a hole, not a feature — and one that pays a multiplier, i.e. exactly where cheating is worth it. So Blind is absent from the scoring set. It remains a fine *solo practice* idea and could ship as an unscored self-challenge · revisit: if a verifiable proxy is found (there isn't an obvious one), or if it ships unscored.
- **D-24 · Declarations are per-seat and generator-proved, never a fixed menu** · The first implementation offered all four gambits on every level. Measurement across twelve curated levels found "two-body" had **zero** winning shots on three of them — the game would have been inviting a bet it could not pay. The generator now proves feasibility from the solver sweep it already runs (free: the measurements live on `ShotResult` and the sweep already simulates every sample to completion) and publishes a per-seat bitmask. Per seat, not shared: intersecting the two seats' masks left *half of sampled duels with no declarations at all*, and the two stations genuinely face different fields; seat fairness is already enforced by the hit-rate ratio check. The proving sweep is coarse, so it under-reports rather than over-reports — an offer that exists is always winnable · revisit: if a finer sweep becomes cheap enough to widen the menus.
- **D-25 · A kept declaration multiplies DAMAGE in duels, not style points** · First pass multiplied `styleBonus`, which duels never read — duel outcome is HP only. That made declaring in PVP pure downside: all of the risk (a broken declaration wastes the turn) and none of the reward. Damage multiplication puts the payout in the currency the mode actually settles in · revisit: after PVP playtesting, if 2.2x damage proves too swingy against the 100 HP pool.
- **D-26 · Capture is an orbital-INSERTION puzzle, because the physics left no other option** · The objective was specified as "achieve a stable orbit for N ticks". Building it first required measuring whether that is reachable at all, and it is not by aiming alone: a shot arriving from far away is on a hyperbolic trajectory, and a two-body encounter with no dissipation cannot capture — it must leave. Measurement agreed: across twelve generated levels no unbraked shot exceeded 191 ticks of ring dwell, and every refined optimum pinned against the game's slowest launch, i.e. the search wanted a speed the game does not offer. The RETRO brake is the only dissipation in the game, and with it the same levels reached 339–818 ticks. So Capture *requires* a burn, the threshold is set at 240 (above the 191 a flyby can reach, so a flyby can never satisfy it by accident — the `fallsToNaiveShot` principle), and a Capture system issues a RETRO shell regardless of loadout, since the objective demanding a tool it may not have unlocked would be a dead end. Side effect worth having: this is the first thing in the game that gives the RETRO shell a purpose · revisit: if dissipation is ever added elsewhere (atmospheric drag, debris), unbraked capture becomes possible and the 240 bar must be re-measured.
- **D-27 · Objectives are campaign-only, and assigned only when proved winnable** · A duel is a contest between two players and the daily is a score gauntlet; "hold an orbit" is neither, and retrofitting it would change what those modes are. Within the campaign, an objective is assigned only after the generator finds an actual solution (`proveCapture`, first-hit early exit, ~28% roll at difficulty ≥2, worst measured generation 280ms). A failed proof silently leaves the system a Breach. This is D-24 applied a second time: the game must never set a task it cannot confirm is achievable · revisit: when Thread/Courier land, each needs its own proof.
- **D-28 · One generic `markedBody`, not a field per objective** · Capture needs a world to orbit; Courier needs a comet to strike. Adding `captureBody` then `courierBody` would have meant a new `SystemSpec` field, a new `LiveShot` parameter and a new branch for every objective that points at something. One `markedBody` plus a per-objective `objectiveSatisfiedBy` keeps the cost of the next objective to an enum entry, a proof and a rule. Objective assignment now collects *all* proved-payable objectives for a system and picks among them from the seed, so adding one does not require touching the assignment logic either · revisit: if an objective ever needs to mark two things (Thread's gates will — it needs an ordered list, so it gets its own field rather than being forced through this one).
- **D-29 · Duels normalize: both players are issued every shell and the top preview** · Audit found the game was already selling PVP advantage while DESIGN.md claimed it was not — the preview upgrade (✦250/✦600, 90→270 ticks of look-ahead) applied in duels, and Breaker's 50 damage vs Bolt's 34 sat behind ✦900 of purchasable stardust. The deeper problem is that this game *cannot referee loadouts*: a duel travels as (seed, turns, hash) and the receiver re-simulates it, so it can verify the physics but never the shopping — a claimed loadout is taken on trust, the D-23 hole except deciding who wins. And with no matchmaking there is no ladder to absorb a paid edge. So duels issue everything to everyone, unconditionally; progression lives in Campaign/Daily/Expedition. This is not a revenue sacrifice, it is what *permits* aggressive monetization of the season track without any of it being pay-to-win · revisit: only if accounts + a server + trophy matchmaking ever exist (D-2 reversed).
- **D-30 · Long-term progression is a seasonal track, not card levels** · The owner asked for Clash Royale-style levelling and non-cosmetic purchases. CR's model is server-authoritative stats plus trophy matchmaking; we have neither by design, and stat progression is unverifiable here (D-29). A 28-day, 50-tier season track fed by verified play delivers the same "long tail worth returning to" while staying decidable offline as a pure function of (epochDay, xp). Free lane + a per-season consumable pass (`season_pass`), additive and retroactive, with **no buy-tiers product** — a track you can pay to skip is a receipt, not progression. Tier curve is calibrated against a modelled play rate rather than chosen: the first attempt needed a committed player 69 days to finish a 28-day season, which `SeasonTest` caught · revisit: after live retention data; the curve is one constant.
- **D-31 · Thread's gates are derived from a real trajectory, not scattered** · Scattering three gates and hoping one shot takes all of them in order gives no reason to believe a solution exists — and "in order" is the objective, so a level that cannot be threaded is a level that cannot be finished. The generator instead flies a trajectory first, samples it at spaced ticks and hangs a gate perpendicular to travel at each, with a small random offset so the flight does not pass dead through every centre (which would read as a rail rather than a route). Feasibility is then **re-proved independently** by `proveThread`, which sweeps for *any* passing shot without reference to the source flight: "we built these from a path" and "a player can find a path" are different claims, and only the second matters (D-27). Gates live in their own `SystemSpec.gates` rather than `markedBody`, per D-28 — a sequence is not a single target · revisit: gate width (78 half-width) if playtest says threading feels like threading a needle.
- **D-32 · Owner direction set 2026-08-06 (four answers that steer everything after Stage C)** · (a) **Cadence: alternate features and launch prep** rather than a feature freeze — so each unit should advance one or the other, and presentation work is preferred where it does both. (b) **Expedition is ADDITIVE, not a replacement** — VISION §3.6 says it should replace the sector checklist; the owner's call is to keep the campaign as the teaching/progression spine and add Expedition as a third PVE mode. That preserves stars, sector gating and the unlock ladder the season references, and removes the save migration. VISION §3.6 is amended accordingly rather than followed. (c) **Difficulty target: demanding — mastery is the point.** Current calibration stays; do not soften bands, the three-star rule, or objective thresholds to widen the audience. Losing casual players early is an accepted cost of the honest-physics identity. (d) **Presentation gets real investment** — it is a storefront product, first impressions decide installs, and screenshots sell the listing · revisit: (c) after real retention data; (a) once a launch date exists.
