- **D-22 · Orbital motion (v2) needs NO engine restructuring — assessed 2026-08-04, not built** · Question: does `MatchEngine`/`LiveShot` need reworking before bodies can move? Assessment: **no**. Body positions are read in exactly two places in the hot loop (`integrate` gravity accumulation, `collide` overlap test) and nowhere else in the rules; `Body` is already an immutable value type, so motion is a pure function `pos(tick)` rather than mutable state — determinism is preserved for free provided the position function uses only the sanctioned operations (StrictMath, doubles; see DETERMINISM.md) and takes the *integer tick* as its input, never wall-clock. Required changes are additive: (a) `Body` gains orbit params (centre, radius, angular velocity, phase) with static bodies as ω=0; (b) the two hot-loop reads call `bodyX(b, tick)`/`bodyY(b, tick)`; (c) `RenderCache` must stop precomputing body centres and instead cache only orbit *geometry* (per-frame positions become cheap trig — measure before shipping); (d) the solver already re-simulates per candidate so it keeps working unchanged, though generation cost rises since layouts can no longer be pre-culled by static geometry. **Blocking consequence**: every existing share code breaks, so this is a `ShareCodec` VERSION bump (TUNING.md §Versioning) and — post-1.0 — a SemVer MAJOR. Verdict: build it when the gameplay is worth the protocol break, not before; no preparatory refactor is justified now, and doing one speculatively would add indirection for a feature that may never ship.
- **D-23 · Gambits are scored ONLY if the simulation can verify them; "Blind" is cut** · VISION.md §3.2 proposed four declarations including *Blind* (fire with no aim preview). Three of the four are properties of the flight — power used, bodies passed, path relative to the launch→target line — and a peer re-running the physics from a share code derives them itself. *Blind* is not: nothing in a `TurnInput` records whether the sender looked at their preview, so a receiving device would have to take the claim on trust. In a game whose entire premise is that nothing is taken on trust (D-2, D-4), a scoring rule that only works if everyone is honest is a hole, not a feature — and one that pays a multiplier, i.e. exactly where cheating is worth it. So Blind is absent from the scoring set. It remains a fine *solo practice* idea and could ship as an unscored self-challenge · revisit: if a verifiable proxy is found (there isn't an obvious one), or if it ships unscored.
- **D-24 · Declarations are per-seat and generator-proved, never a fixed menu** · The first implementation offered all four gambits on every level. Measurement across twelve curated levels found "two-body" had **zero** winning shots on three of them — the game would have been inviting a bet it could not pay. The generator now proves feasibility from the solver sweep it already runs (free: the measurements live on `ShotResult` and the sweep already simulates every sample to completion) and publishes a per-seat bitmask. Per seat, not shared: intersecting the two seats' masks left *half of sampled duels with no declarations at all*, and the two stations genuinely face different fields; seat fairness is already enforced by the hit-rate ratio check. The proving sweep is coarse, so it under-reports rather than over-reports — an offer that exists is always winnable · revisit: if a finer sweep becomes cheap enough to widen the menus.
- **D-25 · A kept declaration multiplies DAMAGE in duels, not style points** · First pass multiplied `styleBonus`, which duels never read — duel outcome is HP only. That made declaring in PVP pure downside: all of the risk (a broken declaration wastes the turn) and none of the reward. Damage multiplication puts the payout in the currency the mode actually settles in · revisit: after PVP playtesting, if 2.2x damage proves too swingy against the 100 HP pool.
- **D-26 · Capture is an orbital-INSERTION puzzle, because the physics left no other option** · The objective was specified as "achieve a stable orbit for N ticks". Building it first required measuring whether that is reachable at all, and it is not by aiming alone: a shot arriving from far away is on a hyperbolic trajectory, and a two-body encounter with no dissipation cannot capture — it must leave. Measurement agreed: across twelve generated levels no unbraked shot exceeded 191 ticks of ring dwell, and every refined optimum pinned against the game's slowest launch, i.e. the search wanted a speed the game does not offer. The RETRO brake is the only dissipation in the game, and with it the same levels reached 339–818 ticks. So Capture *requires* a burn, the threshold is set at 240 (above the 191 a flyby can reach, so a flyby can never satisfy it by accident — the `fallsToNaiveShot` principle), and a Capture system issues a RETRO shell regardless of loadout, since the objective demanding a tool it may not have unlocked would be a dead end. Side effect worth having: this is the first thing in the game that gives the RETRO shell a purpose · revisit: if dissipation is ever added elsewhere (atmospheric drag, debris), unbraked capture becomes possible and the 240 bar must be re-measured.
- **D-27 · Objectives are campaign-only, and assigned only when proved winnable** · A duel is a contest between two players and the daily is a score gauntlet; "hold an orbit" is neither, and retrofitting it would change what those modes are. Within the campaign, an objective is assigned only after the generator finds an actual solution (`proveCapture`, first-hit early exit, ~28% roll at difficulty ≥2, worst measured generation 280ms). A failed proof silently leaves the system a Breach. This is D-24 applied a second time: the game must never set a task it cannot confirm is achievable · revisit: when Thread/Courier land, each needs its own proof.
- **D-28 · One generic `markedBody`, not a field per objective** · Capture needs a world to orbit; Courier needs a comet to strike. Adding `captureBody` then `courierBody` would have meant a new `SystemSpec` field, a new `LiveShot` parameter and a new branch for every objective that points at something. One `markedBody` plus a per-objective `objectiveSatisfiedBy` keeps the cost of the next objective to an enum entry, a proof and a rule. Objective assignment now collects *all* proved-payable objectives for a system and picks among them from the seed, so adding one does not require touching the assignment logic either · revisit: if an objective ever needs to mark two things (Thread's gates will — it needs an ordered list, so it gets its own field rather than being forced through this one).
- **D-29 · Duels normalize: both players are issued every shell and the top preview** · Audit found the game was already selling PVP advantage while DESIGN.md claimed it was not — the preview upgrade (✦250/✦600, 90→270 ticks of look-ahead) applied in duels, and Breaker's 50 damage vs Bolt's 34 sat behind ✦900 of purchasable stardust. The deeper problem is that this game *cannot referee loadouts*: a duel travels as (seed, turns, hash) and the receiver re-simulates it, so it can verify the physics but never the shopping — a claimed loadout is taken on trust, the D-23 hole except deciding who wins. And with no matchmaking there is no ladder to absorb a paid edge. So duels issue everything to everyone, unconditionally; progression lives in Campaign/Daily/Expedition. This is not a revenue sacrifice, it is what *permits* aggressive monetization of the season track without any of it being pay-to-win · revisit: only if accounts + a server + trophy matchmaking ever exist (D-2 reversed).
- **D-30 · Long-term progression is a seasonal track, not card levels** · The owner asked for Clash Royale-style levelling and non-cosmetic purchases. CR's model is server-authoritative stats plus trophy matchmaking; we have neither by design, and stat progression is unverifiable here (D-29). A 28-day, 50-tier season track fed by verified play delivers the same "long tail worth returning to" while staying decidable offline as a pure function of (epochDay, xp). Free lane + a per-season consumable pass (`season_pass`), additive and retroactive, with **no buy-tiers product** — a track you can pay to skip is a receipt, not progression. Tier curve is calibrated against a modelled play rate rather than chosen: the first attempt needed a committed player 69 days to finish a 28-day season, which `SeasonTest` caught · revisit: after live retention data; the curve is one constant.
- **D-31 · Thread's gates are derived from a real trajectory, not scattered** · Scattering three gates and hoping one shot takes all of them in order gives no reason to believe a solution exists — and "in order" is the objective, so a level that cannot be threaded is a level that cannot be finished. The generator instead flies a trajectory first, samples it at spaced ticks and hangs a gate perpendicular to travel at each, with a small random offset so the flight does not pass dead through every centre (which would read as a rail rather than a route). Feasibility is then **re-proved independently** by `proveThread`, which sweeps for *any* passing shot without reference to the source flight: "we built these from a path" and "a player can find a path" are different claims, and only the second matters (D-27). Gates live in their own `SystemSpec.gates` rather than `markedBody`, per D-28 — a sequence is not a single target · revisit: gate width (78 half-width) if playtest says threading feels like threading a needle.
- **D-32 · Owner direction set 2026-08-06 (four answers that steer everything after Stage C)** · (a) **Cadence: alternate features and launch prep** rather than a feature freeze — so each unit should advance one or the other, and presentation work is preferred where it does both. (b) **Expedition is ADDITIVE, not a replacement** — VISION §3.6 says it should replace the sector checklist; the owner's call is to keep the campaign as the teaching/progression spine and add Expedition as a third PVE mode. That preserves stars, sector gating and the unlock ladder the season references, and removes the save migration. VISION §3.6 is amended accordingly rather than followed. (c) **Difficulty target: demanding — mastery is the point.** Current calibration stays; do not soften bands, the three-star rule, or objective thresholds to widen the audience. Losing casual players early is an accepted cost of the honest-physics identity. (d) **Presentation gets real investment** — it is a storefront product, first impressions decide installs, and screenshots sell the listing · revisit: (c) after real retention data; (a) once a launch date exists.
- **D-33 · Ambience is synthesized from the system at runtime, and the loop length is set by the pulsar, not by taste** · The game had no music at all, and could not simply get some: every level comes from a seed, so there is no finite set of places to score. One shared loop would say nothing about where you are, so the pad is derived from the board — a voice per body, pitch from mass, phase from position, harmony set from the objective. Two consequences fall out. **(a) It costs zero APK bytes** and, on `MODE_STATIC` with hardware loop points, zero CPU while playing. **(b) The seam has to be exact**, since a click every seven seconds is worse than silence — so periodicity is stored as *integer cycles per loop* rather than hertz, making seamlessness a property of the type. That normally detunes the intervals; it does not here because every root is a multiple of 80 cycles and every ratio denominator divides 80, so exact just intonation and an exact seam hold simultaneously with no rounding. **The seven-second loop is not a taste decision**: `PULSAR_PERIOD × DT` is exactly 3.5s of real gravity oscillation, and 7 is the smallest whole number of seconds holding a whole number of those — which is what lets a pulsar's tremolo stay phase-locked across every repeat, forever. `AmbienceTest` fails loudly if a future retune of `PULSAR_PERIOD` breaks that divisibility, because the game would otherwise go on claiming the pad tracks the pull. Ambience is **excluded from the determinism contract on purpose** (never hashed, never on the wire): the day verification depends on an audio buffer is the day audio tuning becomes a protocol break. `musicEnabled` is separate from `soundEnabled` because wanting impacts and wanting a drone are different wants · revisit: after someone has actually sat inside a loop for five minutes — the open questions are listed in AUDIO.md §7.
- **D-34 · Expedition is a wrapper around campaign matches, and travel cost — not shot cost — is what ends a run** · Two decisions, both forced by constraints rather than chosen. **(a) A leg is an ordinary `GameMode.CAMPAIGN` match.** Given D-32b makes Expedition additive, the cheapest correct shape is state carried *between* existing matches rather than a new match mode: nothing reaches `MatchEngine`, `ShareCodec` or the determinism contract, so a whole new mode cost the replay protocol zero and needed no version bump — and D-27 ("objectives are campaign-only") stays true by construction, since an Expedition leg *is* a campaign match and is therefore entitled to objectives. A `GameMode.EXPEDITION` would have meant a codec value, engine branches, and re-deciding objective eligibility, for nothing the player can see. **(b) The economy escalates travel, not shots.** The first draft put the clock on shot cost; `runsAlwaysEnd` failed immediately and taught the design — a per-shot cost cannot clock a player who fires *one* shot, so a perfect run hit the leg cap with a full tank and the mode was an idle game with extra steps. Travel cost rises linearly and without bound while refunds are bounded above by a `MAX_REFUND` **derived from the route/mutator tables rather than typed in**, so past `BLEED_DEPTH` every leg is a net loss no matter how perfectly it is played: termination is an argument from arithmetic, and the test checks it against the best player the rules permit rather than an expected one. Consequences: a wreck advances the run rather than ending it (ending on one bad system makes the opening minute the whole game and punishes the player who took the hard route); mutators are **run rules, never generator requests**, because a "binary star ahead" the generator cannot produce in band would leave the run claiming a condition that never applied — the D-24/D-27 failure exactly; and the meta-currency is **stardust**, since minting an unspendable token before the thing it buys exists is a number that goes up and means nothing. Side effect worth having: **Blind ships at last**, as the *Dark run* mutator — D-23 cut it because no peer can verify a sender ignored their preview, an objection about verification by a stranger that simply does not apply to a solo run that sends nothing · revisit: run length is *modelled*, not measured (expert 27 legs, steady 22, rough 15 under stated archetypes) — the first playtest decides whether that is a sitting or a chore, and it is one constant.
- **D-35 · Motion is decoration and obeys the system setting; information never is** · Android lets a user zero the animator duration scale, and accessibility guidance tells people with vestibular disorders or motion sensitivity to do exactly that. The system then stops running *animators* — but it cannot stop a game that draws its own motion frame by frame, and ours does: the camera shake shipped in 0.13.1 as hand-drawn translation, so from that version until 0.16.2 a player who had switched animations off system-wide still got the board thrown around on every kill, with no in-app switch to stop it. The gap was invisible because nothing fails when an accessibility setting is ignored. `ui/Motion.kt` reads `ValueAnimator.areAnimatorsEnabled()` once per composition scope (the setting cannot change without leaving the app, so per-frame reads would burn a binder call for a constant) and both the shake and the new star flourish honour it. **The line is drawn at decoration versus information**: the projectile still flies, the trail still draws, the preview still updates, and where a flourish would otherwise *reveal* something — the stars — the finished state is drawn at once rather than not at all. "Reduced motion" means do not decorate with movement; it never means hide what is happening. Corollary for future work: any new hand-drawn animation must ask, and any that conveys state must degrade to its end state rather than to nothing · revisit: if a player ever wants finer control than the system toggle, this becomes an in-app setting — but a second switch that duplicates a system one is worse than no switch, so not before someone asks.
- **D-36 · The shop may only promise what the protocol can deliver; the season pass is not a grind-skip** · Ninth audit pass, on the two screens that take money and had never been checked. Two false claims, both inducements. **(a) "Your rival sees these in the replay"**, printed above the trail catalogue — they do not. `GameScreen` draws an opponent's replay with the *classic* trail, because a share code carries `(seed, turns, hash)` and the receiving device regenerates everything else from the seed. A cosmetic choice never crosses the wire. This is the same limit that cut Blind (D-23) and forced duel normalization (D-29), reaching a third area: **the code carries moves, not the shopping**, and here it was being used to sell something. Copy corrected to what is true. Making it *true* instead — putting a trail id in the payload — is a live option and is recorded in TODO with its costs: a protocol version bump invalidating every code in the wild, plus cosmetic data taken on trust (harmless, since nothing is decided by it). Worth doing cheaply *now* if at all, since nothing has shipped; not a call to make silently inside an audit. **(b) "Everything above is earnable by playing. These just skip the grind."** is true of the stardust catalogue but was about to become false, because the shop listed every product unfiltered and `season_pass` is one — and the premium lane cannot be earned at any amount of play. It is the one product that grants content rather than accelerating it. Filtered out of that section; it keeps its own screen, where the offer is shown in full before it is bought. `CosmeticReachTest` now states both facts structurally, so the next person to write shop copy has something to check against rather than an assumption to inherit · revisit: (a) if the owner wants trails to travel, which is a protocol decision.
- **D-37 · Every screen that promises a reward or an outcome is checked against the rules, and the rules live in the test** · Tenth audit pass, finishing the player-facing screens (Help 0.16.1, Shop 0.16.3, Season+Duel here). Two more wrong claims, both about *what the player gets or how it ends*. **(a) "Play anything: campaign, the daily, or a duel. Everything counts."** Wrong twice: it omitted Expedition, which does pay (`Season.expeditionXp`), and it counted "a duel" flat when `Season.duelXp` pays **zero** for hot-seat — the same self-farm guard that makes hot-seat pay no stardust. A player grinding hot-seat for tiers would have earned nothing while the screen said everything counts. **(b) "First station down loses."** True as a win condition, incomplete as an ending: a duel is also over at `DUEL_MAX_TURNS` with both alive, and `duelWinner()` returns null there — a draw the screen never mentioned, reachable by two players who keep missing, who are exactly the players in their first duel. Both corrected, and hot-seat's zero payout is now stated where a player decides to play it rather than discovered afterwards. **The pattern across all four screens**: every false claim was about a *number, a reward or an outcome* — never about flavour. Flavour cannot be wrong; a promise can. So the guard is `RewardReachTest`, in `:core` rather than in a screen test, stating which activities pay and how a duel can end — a screen should be checked against the rules, not the rules inferred from a screen. One claim was checked and **found true** ("the second reward at every tier" — `premiumReward` has an `else`), recorded as verified because a claim checked and a claim assumed are different states · revisit: whenever a mode, reward or ending is added — the copy is not done until the promise is checked.
- **D-38 · Expedition progression uses its own currency, and every upgrade had to survive the termination proof** · D-34 shipped the run mode paying stardust only, on the grounds that minting an unspendable token before the thing it buys exists is a number that goes up and means nothing. This is the other half — the things to buy — and it changes the currency. **Salvage is separate from stardust because stardust is buyable with real money** (`Iap.STARDUST_SMALL`/`_LARGE`). Pricing run upgrades in stardust would let money buy Expedition depth; that breaches no PVP invariant (D-13/D-29 is about duels, and Expedition is solo), but **a personal best that can be topped up at the till is a weak personal best**, and "how far did *you* get" is the whole pull of the mode. Salvage is earned only by running and spent only on running, so the loop closes on itself. It is also deliberately **not** multiplied by the Ad Pass, for the same reason. **The harder constraint was D-34's proof that runs provably end** — permanent upgrades are exactly the sort of feature that voids such a proof quietly. Two obvious options were cut for it: *cheaper travel* (even a constant discount leaves termination intact, but it makes the proof depend on a purchase, which is a bad thing to owe a receipt) and *junction rerolls* (they break the rule that a junction is a pure function of seed+depth, which exists so leaving and returning cannot fish for a better offer). What shipped changes only the **tank** and the **refunds**, both bounded, so travel still outgrows everything: reserve tank (+5 fuel/tier ×3), salvage rig (refunds part of a wrecked leg's *shot* cost — never its travel, since travel is the clock), and survey array (pure information: read the next junction, moves no number in the economy, which is why it can be the expensive one). `OutfittingTest.runsAlwaysEndEvenFullyOutfitted` re-runs the best-possible-player argument with everything maxed. **Numbers corrected 0.19.4**: this recorded "depth 32 against 29 bare", which were single-seed observations. Swept across 500 seeds the proof still holds everywhere — no run is unbounded and none hits the leg cap — but the *worst cases* are deeper than one seed showed: **35 bare and 36 outfitted against a cap of 40**, i.e. 4 legs of headroom rather than the 8 the old figures implied (D-42's lesson applied to this proof). Ladder calibrated at ~8.3 good runs, modelled and stated like D-30's tier curve · revisit: if playtest says the ladder is a wall or a formality; the band asserted is 4–20 runs.
- **D-39 · Stage F debris is measured before it is written, and the measurement rewrote the rule** · VISION §3.3 promised "a shot that dies leaves debris: a small permanent body at its death point — miss twice and you have complicated your own board". Four measurements (`DebrisMeasurementTest`) took that apart before a line of the rule was written. **(a) The obvious sample was the wrong sample.** Swept over the solver's uniform 360° grid, 86% of shots leave the field and only 12–19% die on the board, which reads as "debris is inert, the mechanic is dead". But the solver grid includes firing directly away from the target into empty space, and a player does not do that. Re-sampled inside a realistic aim cone the number **inverts: 57–80% of misses die on a body**. Debris would not be rare, it would be constant — the opposite conclusion from the same simulator, decided entirely by which shots you ask about. **(b) A shot has essentially one way to die on the board, and that is hitting a body.** In 18,000 grid samples: 2,625 body deaths, **1** own-station death, **0** timeouts. So debris can never be planted in open space, only against something already solid — the rule cannot create a new obstacle in an empty lane, no matter how it is phrased. The own-station case is real but pathological (a lump welded to your own launch point), and is excluded by spawning on body impact only. **(c) The physically honest version is invisible.** Area-conserving accretion — add the shell's cross-section to the body it struck — moves a radius-100 planet to 100.12, and across 16 hits at every difficulty the solve rate did not shift by a single sample. Real bodies are radius 58–101 against a radius-5 Bolt; conserved matter simply cannot register. So debris has to be a **gameplay abstraction sized for legibility, not conserved mass**. **(d) What works is that it is directional.** Growing a radius is isotropic and says nothing; a free-standing lump at the impact point sits on the side the shot came from, so it blocks *the approach you keep taking* — which is what "the arena degrades into something neither player designed" actually means. Measured against solvability it erodes gradually and scales with size: at radius 12 a level retains 50–100% of its winning shots after 30 lumps, at radius 20 only 33–67%. **[SUPERSEDED BY D-42]** This decision recorded that *nothing stranded the player* in any of 27 configurations and had `measureStrandingAtFullMatchLength` assert it. That claim was true of the **nine levels** it sampled and false in general: widening to 30 levels found two that a littered board makes unwinnable, earliest at 13 wrecks. The severity is bounded — campaign (≤3 wrecks) and daily (≤4) cannot reach it, so no objective can be stranded (D-27); only a duel can, where it is a draw at the turn cap. The measure was otherwise conservative as stated (STANDARD shells, one station, no anchors). Recommended size is **radius ~12, mass 0** — visible, directional, erosive, never fatal. **Method note worth keeping**: the first version of the structural assertion read "0.0%" off a formatted column and asserted zero; the raw count was 1. A rounded display is not data · revisit: after implementation, on whether debris should also *pull* — mass was held at 0 here deliberately so obstacle and gravity were not conflated in one measurement.
- **D-40 · Debris is derived, not transmitted — and the rules that bound it were chosen against the measurement, not against the sentence** · Stage F shipped from D-39's numbers rather than from VISION §3.3's original wording, which those numbers had already contradicted. **(a) The protocol insight: a wreck costs zero bytes.** Debris is a pure function of turns the share code already carries, and `MatchReplayer` drives the same `beginShot`/`commit` path as live play, so a verifier re-derives identical wrecks without a byte crossing the wire. This is the first protocol bump that spends nothing — v2–v8 each changed what a code *carries* or what a seed *generates*; v9 changes only what a code **means**. It is still a full bump, because the same (seed, turns) now produces a different match and a pre-v9 code would verify against a board that no longer exists. Debris is folded into the match hash regardless, since two devices that somehow derived different wrecks must not be able to agree on the outcome by accident. **(b) Four bounding rules, each closing a specific failure.** A station kill leaves nothing (an outcome, not a crash — and it excludes the own-station lump that D-39 measured at 1 in 18,000: rare, real, and a self-inflicted dead end). One wreck per turn even from a Triad's three shards (per-shard litter triples a duel's accumulation and leaves the envelope that was actually measured). A wreck settles against a world, never another wreck, so accumulation stays linear rather than compounding. And **debris is inert for scoring** — excluded from the deflector count and the graze bonus — which is the one that would have been a real bug rather than an imbalance: `deflectorCount` decides the "two-body" gambit, so a massless lump counting as a deflector would let a declaration be honoured by a deflection that never physically happened, the D-23/D-36 "the game must not claim what did not occur" line reaching a fourth area. **(c) The objective gap had to be closed separately.** D-39 measured whether a littered board still has a shot that hits the enemy *station*; three of four objectives are not won that way, and they are the fragile ones — a wreck can fence a capture ring or block a gate. 29 objective systems (13 Capture, 12 Thread, 4 Courier) were littered at the reachable campaign envelope and re-proved with the generator's own `proveCapture`/`proveThread`/`proveCourier`: none became unwinnable. D-27's bar now covers boards the *player* littered, not only boards the generator authored. **(d) Two things found by following the change outward rather than by testing it.** The aim preview was reading `spec.bodies` and would have drawn a trajectory through a field the shot was never going to meet — the instrument the player judges a shot with, quietly out of date. And the daily's target relocation reads `spec.bodies` too, which looked like the same hole but is closed by arithmetic already present: a relocated target sits ≥ `bodyRadius + 76` from a body centre while a wreck sits ≤ `bodyRadius + 9` from it, a gap of ≥67 against the 38 needed to overlap — now pinned in a test, because it is only true while those constants hold · revisit: whether debris should also *pull*, deliberately left unmeasured so obstacle and gravity were not conflated; and `DEBRIS_RADIUS`, which is bounded above by `measureStrandingAtFullMatchLength` rather than free.
- **D-41 · The store's screenshot list is a set of claims about the artifact, and one of them named a thing that does not exist** · Work started as presentation polish for the shots in STORE_LISTING, and ran immediately into an honest limit: *"the money shot — retake until beautiful"* is a question for eyes, and an agent has none. What is not a question for eyes is **reaching** the moment — a Capture system is a ~28% roll, and a slingshot worth photographing needs a particular shot on a particular board. Grinding for those is why the screenshot task drags, and Play will not accept a listing without them. So the deliverable became a **catalogue of coordinates**: real (sector, level) pairs a human navigates to, plus the exact aim where one is needed (slingshot: sector 4 level 11, angle 3060 power 300, gain 230 passing 25u from a surface; Capture: sector 1 level 2, angle 2360 power 1000, brake at tick 40, dwell 334 against a bar of 240). **The find is that shot 2 asked for a "binary-star field", and this game has no binary stars.** The generator emits at most one `STAR`: `keeperIsStar` picks one keeper, and the `doubleKeeper` path adds a second large **PLANET**, never a second star. Measured across 720 generated systems the star-count histogram is `{0: 93, 1: 627}` — maximum 1, confirmed both by sampling and by reading the placement code. Anyone hunting that screenshot would have hunted forever. Two more docs carried the same fiction: DESIGN.md said the generator composes *"a system (star or binary, …)"*, and PERFORMANCE.md named *"a Triad shot over a binary-star field"* as the jank-hunting worst case — a benchmark scenario that cannot be set up, which means the stated worst case was never the worst case. The correction is a **double keeper** (two massive bodies), which does exist and is the honest equivalent. Note what makes this a different catch from the ten doc audits: **D-34 already knew**, citing "a *binary star ahead* the generator cannot produce in band" as the very reason field-shaping mutators need a proof — so the decision log and DESIGN.md had contradicted each other for months, and the store listing built a requirement on the wrong one. A claim can be false even when another document in the same repository already says so. The catalogue is now asserted rather than published-and-trusted (`ScreenshotSeedsTest`), because a coordinate rots the instant generation changes and nothing fails when it does; the guard includes an inverted check that fails if a real binary ever *starts* existing, since at that point the corrected copy becomes the false one · revisit: re-run after any generator change — the test says so, and the doc says so.
- **D-42 · Debris does not pull — and the "nothing strands" claim behind D-39/D-40 was true only of the nine levels it sampled** · Two findings from one measurement, and the second one corrects work I shipped two versions earlier. **(a) The answer to "should a wreck pull?" is no.** Mass was deliberately held at 0 in 0.18.0 so obstacle and gravity were not conflated. Measured now across 30 levels per mass, massive debris drives levels to a *zero* solve rate — and the crucial detail is that it does so **non-monotonically**: 1e4 stranded 3/30, 2.5e4 stranded 2/30, 5e4 stranded 0/30, 1e5 stranded 1/30, 2e5 stranded 2/30. There is no "safe if small" threshold to tune toward, because small is not safer. That is the signature of compounding — a massive wreck bends later shots, which changes where they die, which places the next wreck somewhere the clean board never would have — and it is exactly why D-40 refused to inherit the massless safety argument. A mechanic whose safety cannot be tuned is not a mechanic worth having for a nudge to the field. **(b) The measurement caught itself lying first.** The initial run reported *identical* numbers for every mass including 2e5, which reads as "mass is irrelevant, ship either way". The cause was that 0.18.0 makes the integrator skip `BodyKind.DEBRIS` whole, before the arithmetic, precisely because a shipped wreck is massless — so building the probe out of `DEBRIS` measured nothing at all. Modelling a massive wreck as what it physically is, a small dense `PLANET`, produced the real answer. Rows that agree *too* exactly are evidence of a disconnected instrument, not of a robust result. **(c) The correction that matters more.** Widening the sample from 9 levels to 30 showed the **shipped, massless** configuration also stranding — 2 of 30 — so D-39's "nothing stranded the player in 27 configurations" and D-40's inheritance of it were never general claims; they were claims about a sample, with the sample size dropped. `measureStrandingAtFullMatchLength` passed only because its 9 levels happened to exclude the failures. Follow-up measurement puts the earliest stranding at **13 wrecks**, which resolves the severity honestly rather than either hiding it or overstating it: campaign caps at `CAMPAIGN_SHOTS` (≤3 wrecks) and daily at `DAILY_SHOTS` (≤4), so **neither can reach it**, and since objectives are campaign-only (D-27) no objective can be stranded. Only a duel can, at ≤30 turns, where an unwinnable board is a **draw at the turn cap** — an outcome D-37 already documented — rather than a dead end a player cannot leave. So the shipped behaviour stands, but the *claim* about it was wrong and the guard has moved: the assertion is now that stranding stays out of campaign reach, which is the bar that carries consequences · revisit: if duel draws by mutual littering ever show up as a real complaint, the lever is `DEBRIS_RADIUS` or a per-match wreck cap — but that is a playtest question, not an arithmetic one.
- **D-43 · Blind ships unscored — and building it found that the mode which already "shipped Blind" never actually did** · D-23 cut *Blind* from the scored Gambits because nothing in a `TurnInput` records whether the sender looked at their preview, so a peer verifying a share code would take the claim on trust — a hole in a game whose premise is that nothing is (D-2, D-4). It closed with "it remains a fine solo practice idea and could ship as an unscored self-challenge", and that is what shipped here: a Settings toggle that removes the aim trace **everywhere, including duels**, and **pays nothing** — no bonus, no multiplier, no star, nothing recorded, nothing transmitted. The objection was always about *verification by a stranger*, and a handicap that grants no reward gives a stranger nothing to verify. Blind practice is checked **before** the duel branch on purpose: a duel normally guarantees both players the top preview (D-29), but that rule exists to stop anyone being *disadvantaged*, and it must not override a disadvantage the player chose. **The find is that Expedition's *Dark run* mutator had been lying since 0.15.0.** Its own description says "No aim trace on this system" and D-34 recorded it as "Blind ships at last" — but `previewLevelFor` returned tier **0**, which is not blindness, it is the base 90-tick trace every player owns. The mutator was removing a *purchase* while the copy promised the trace, so a player who bought no preview upgrade experienced a Dark run as no change at all. Fixed by introducing `Economy.PREVIEW_NONE`, a tier that actually means none, with `previewTicks` handling it in an explicit branch rather than by falling through — a negative tier hitting the old `else` would have returned the **best** preview, the exact inverse of the rule. **Why the test did not catch it**: `ExpeditionTest` asserted `previewLevelFor(blind) == 0`, pinning the implementation instead of the claim, so it guarded the bug. It now asserts the result in *ticks*, which is the thing the description promises. Second omission found the same way: **debris shipped in 0.18.0 with no Help entry at all** — a permanent obstacle that appears on the player's own board when they miss, unexplained anywhere in the app for a whole version — and `HelpAccuracyTest` could not fail, because its topic list is hand-maintained and nobody had added a line. Both failures share one shape: **a guard only checks what is enumerated in it**, so adding a mechanic without extending the list makes the guard silently incomplete rather than loudly wrong · revisit: if a verifiable proxy for "did not look" is ever found, blind could become scored — there is still no obvious one.
- **D-44 · Field-shaping mutators cannot ask the generator for anything — but they can *choose a seed*, and that route is honest, protocol-free and self-proving** · D-34 deferred *binary star ahead*, *anchors doubled* and *dense field* on honesty grounds: each asks the generator for a layout it may not produce, so each needs a proof the mutator actually took or the run claims a condition that never applied (D-24/D-27). That reason is real but it is the weaker one. **The binding constraint is architectural**, and `MutatorReachTest` proves it in four cases rather than arguing it. A share code carries `(mode, difficulty, seed, turns, hash)` and nothing else; `decodeAndVerify` regenerates the board from the seed and re-simulates; and **every match can emit a code**, an Expedition leg included, via `MatchController.feedbackCode` — which is how agents triage bug reports. So a mutator that changes *what the board is* produces a leg whose own replay code cannot verify: the receiver rebuilds the unmutated board, gets a different hash, and rejects it as forged. Measured directly: a leg played with one extra body fails `decodeAndVerify`, while an unmutated control passes. **Anchors doubled fails even earlier and worse** — `ShareCodec.decode` enforces `MAX_ANCHORS` as a *rule check*, which is what stops a forged code claiming a match played with more anchors than the game allows; raising that cap to suit one Expedition mutator would weaken verification for **duels**, where verification is what decides who won (D-29). Note this also explains why the two shipped mutators are safe: *Thin reserves* acts on fuel economy and *Dark run* on the aim trace, neither of which a code depends on — now asserted rather than assumed. **The open route is seed selection.** Do not ask the generator for a favour; search its natural output for a seed that *already* satisfies the condition and offer that one. The code then carries an ordinary seed whose plain regeneration reproduces exactly the board played, so verification is untouched — demonstrated by a seed-selected dense leg verifying normally. It also answers D-24 for free: **the search predicate is the proof**, and a search that finds nothing simply does not offer the mutator, which is the honest failure rather than a false claim. **What it costs, measured**: natural body counts run 2–4 at difficulty 2 and 3–8 at difficulty 8+, so *dense field* (≥7 bodies) is **unreachable below about difficulty 6** — 0/60 at d2 and d4, 1/60 at d6, 13/60 at d8, 14/60 at d11 — and a 24-seed search at d4 burns 2061ms to find nothing. Where it does exist it takes ~5 tries and **~390ms desktop**, which is 1–2s on a phone on top of the leg's own generation. So it is buildable, but only deep in a run, and only if the search is paid at junction-offer time rather than at level start · **RESOLVED 0.19.2 — not built, and the arithmetic says why.** Availability was never the problem: an Uncharted leg's difficulty is `min(11, 2 + depth/2)`, so it reaches 6 at **depth 8** and 8 at **depth 12**, giving 3/15 eligible junctions in a rough run, 10/22 steady, 15/27 expert. The problem is that the two honest implementations land on opposite sides of usable. **(a) Generate once and label only if the system genuinely is dense** — costs one generation (~110ms) and can never lie, but the measured hit rate at d≥8 is 13/60, so with Uncharted carrying one of four conditions it appears **0.16–0.81 times per run**: once every two to six runs, which is an easter egg rather than a mechanic. **(b) Search seeds until one is dense** — gives real availability at **0.75–3.75 offers per run**, but costs ~390ms desktop (1–2s on a phone) at a junction, and `Expedition.routesFor` is called *directly in composition*, twice per junction, so it would need memoising just to not repeat per frame. The structural reason neither closes is worth keeping: **knowing what a field looks like requires building it**, which is exactly why field-shaping conditions are expensive in a way the shipped ones are not — *Thin reserves* acts on fuel arithmetic and *Dark run* on the UI, and both are free to evaluate. A condition the player meets twice a year is not worth a second of stall at every junction to enable · revisit: if generation ever gets fast enough that a 24-seed search is cheap, (b) becomes attractive immediately — the route is proved sound, only its price fails.
- **D-45 · Stage E's resonance mechanic has no subject: a player cannot fire "in phase", because every shot resets the pulsar** · VISION §3.4 says *"Pulsars already breathe on fixed periods. Make that a timing mechanic: fire in phase and the assist amplifies; fire out of phase and it fights you."* The first sentence is true; the second describes a choice that **does not exist in the game**. A pulsar's mass is `massAt(tick)` and `tick` is `LiveShot`'s own counter, which starts at 0 for every shot — so every shot ever fired meets a pulsar at `cos(0)`, its heaviest. Phase varies *within* a flight, which is what makes a pulsar interesting to fly past, but never *between* shots. Demonstrated at match level rather than argued from the constant: an identical aim fired as turn one and as turn two is **bit-identical**, same hash and same tick count (`ResonanceReachTest`). There is no timing to get right, so nothing to reward. Note the ambience is *consistent* with this and not implicated — D-33 says playback seeks to sample zero on fire precisely because the pull does too, so "the swell you hear is the pull the shot is flying through" remains true. **What building it would cost**: pulsar phase must become a function of match time rather than shot time, which changes what every existing pulsar level does — a protocol break, not a tuning change — and it touches **27% of systems** (98/360 measured, none below difficulty 4). Worse, making it a *choice* rather than an artefact of turn order needs a timing input recorded in `TurnInput` and folded into the hash, since a phase the sender picks but does not transmit is unverifiable in exactly the way D-23 cut Blind for. **Second finding, same investigation**: TODO's multi-pulsar polyrhythm item said "the generator never makes two with different periods", which reads as *two exist and share a period*. They never co-exist — **0 of 360 systems have two pulsars**. That is the third instance this session of a documented feature whose premise the generator does not produce (binary star D-41, Dark run D-43, this), and the polyrhythm item is therefore blocked on something more basic than a per-body period: there is only ever one pulsar to give a period to · revisit: only alongside a deliberate decision to spend a protocol bump on a timing input; the measurement is banked and the two blockers are now named rather than assumed.

- **D-47 · Nothing in the repository could detect generation output changing, which is the one change that breaks every code in the wild** · Found while preparing to optimise difficulty-11 generation, where TODO's own constraint is that "only optimisations that provably preserve output are allowed" — and there was no way to prove it. The protocol's core assumption is that a seed generates the same board forever: a replay code carries `(mode, difficulty, seed, turns, hash)` and `decodeAndVerify` **regenerates the board from the seed**, so a generator that drifts silently invalidates every code ever shared. What guarded that was `generationIsDeterministic`, which asserts `generate(12345L, 3) == generate(12345L, 3)` — determinism *within one run, on one seed, at one difficulty*. It would pass unchanged if the generator were rewritten to produce entirely different levels. That is D-43's "a guard only checks what is enumerated in it" applied to the most protocol-sensitive code in the project, and it is worse than the earlier instances because the failure is invisible until a stranger's code stops verifying. **Verified rather than asserted, in both directions.** `GenerationFingerprintTest` folds the whole spec — body geometry, masses, kinds, palettes, velocities, stations, gates, objective, marked body, and the measured `solverHitRate`/`anchorLeverage`/`gambitMasks` — across 24 specs spanning six difficulties plus the daily and duel generators, and pins it to one constant. Perturbing a single layout constant by **0.001** (`keeperR` upper bound 86.0 → 86.001) makes it fail; running the **entire** core suite against that same perturbation, **it is the only test that fails** — `ShareCodecTest`, `EndToEndPvpTest`, `GeneratorTest` and `generationIsDeterministic` all pass against a changed generator. Doubles are folded by raw bits because D-4 already guarantees they are bit-stable, so anything looser would hide exactly the drift worth catching. The failure message says what to do, because the tempting fix is the wrong one: a changed fingerprint means either revert, or bump `ShareCodec.VERSION` deliberately and update the constant in the same commit with a decision entry — pasting the new number in turns a protocol break into a rounding error · revisit: extend the spread if a future generator path (a new objective, a new body kind) would not be exercised by these 24 specs.
